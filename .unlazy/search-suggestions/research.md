# Search suggestion source research

## Pass 1 — findings

- Shared implementation: `frontend/src/widgets/ProductSearch/ui/ProductSearchField.tsx`. It owns the focused state, 200 ms query debounce, two catalog queries, merged ordering, rendering, `choose`, and Arrow/Enter/Escape handling. The current `ready` predicate requires authenticated, focused, not dismissed, same debounced/current value, and `value.trim().length >= 2` (lines 57–75). Therefore an empty focused field can never display content from the current query path.
- Current order is device rows first (`device.label`), then catalog product rows (`product.canonical_name`) (lines 76–90). Device/product section headings are currently `Поиск по моделям` and `Поиск по запчастям` (168–171). Product rows use only `canonical_name` (88, 189), and `choose` passes that same name to `onSelect` (95–100). Preserve this selection behavior even if the visible name becomes a structured model + part label.
- The dropdown is absolutely anchored to the field wrapper, with `left-0 right-0` (line 155–161); the wrapper is `relative min-w-0` (102). This already provides the intended width constraint when its parent/field is width constrained. Header wraps it in `w-full` (HeaderSearch.tsx:37–54); authorized home places it in a `max-w-[620px]` flex shell (AuthorizedHero.tsx:80–102). Avoid replacing width constraints with a viewport-wide panel. The list's row text already wraps (`whitespace-normal break-words` at ProductSearchField.tsx:182), and its height/vertical overflow is bounded.
- The existing frontend Zod `catalogSuggestionSchema` only accepts `id` and `canonical_name` (frontend/src/models/catalog/schema.ts:177–182). Backend `CatalogSuggestion` likewise currently exposes these two fields (backend/src/modules/products/schema/comparison.py:163–165). The service query selects only product id/name (backend/src/modules/products/service/comparison_service.py:360–398), despite applying filters through the product/cluster relation. A model-first product caption needs a display field computed from structured relations (device + part type, with sensible fallback when either is absent); do not parse canonical-name strings or use an Apple/iPhone regex allowlist. Keep `canonical_name` separately as the value sent on selection.
- Structured relations are already represented on the catalog item schema: `device` (id/name/model_key/brand_id) and `part_type` (id/code/name_ru) (frontend/src/models/catalog/schema.ts:16–27, 45–55). The stable matching/selection relation is product → cluster → device and part type; service imports and joins live in `backend/src/modules/products/service/comparison_service.py` (around lines 1–40 and 380 onward). `device_suggestions` is distinct and returns `id`, `label`, `model_key`, `count` (same service:148–185); do not fabricate numeric IDs for static popular suggestions.
- Search entry points: `HeaderSearch` and `AuthorizedHero` both pass `onDeviceSelect`; the general `/search` input also uses the shared component through `SearchInput` and may have different props. The empty-state popular panel should not depend on `onDeviceSelect`/auth unless deliberately scoped, since C1 says an empty focused input. Avoid changing the public component props or navigation contracts. The default iPhone entries can call `onSelect('iPhone 15')` etc., which uses the existing `/search?q=...` path; they are search suggestions, not database device entities.
- Existing tests: `ProductSearchField.test.tsx` covers header/home product suggestions, keyboard selection/navigation, submit/clear, and logged-out query suppression. `DeviceSearch.test.tsx` covers device-before-product ordering, selection, and header model-key navigation. For test modifications use the latter shared-widget conventions and keep existing assertions. Backend focused integration coverage is `backend/tests/integration/test_comparison_api.py::test_suggestions_filters_require_active_matching_offers_and_bound_limit` (around 743–789); its exact key-set assertion at 778 must be adjusted for an additive display field. `test_device_search.py` covers device suggestions endpoint independently.

## Pass 2 — expert reread

The smallest safe design is a distinct empty-query state and a query-result state, not a fake product response. For the empty state, render a fixed curated list of query strings headed `Часто ищут`, enabled while the field is focused and not dismissed; make each row an option/button that submits its string through the existing `onSelect` path. For nonempty, valid-length queries preserve the current API-backed device/product list and selection semantics. Ensure dismissal on Escape/click/submit and re-open on focus or edit remain coherent. Enter with no active option must continue submitting the typed value, not select the first suggestion implicitly.

For product suggestions, add an additive backend `display_name` derived from structured `Device`/`Brand` relation data and the existing canonical text, then thread it through backend Pydantic response, frontend Zod/type, and component display. Move the exact model span (including adjacent brand text when present) to the front, retain remaining part/qualifier text in original order, and fall back to `canonical_name` if a structured model span cannot be located. This satisfies model-first without an Apple/iPhone allowlist or lossy replacement with guessed part labels. Keep `canonical_name` as the submitted search query. This is a contract extension, so response-model tests and frontend schema/client checks should be updated.

For width, keep the list inside the search component's relative wrapper; ensure flex ancestors permit shrinking (`min-w-0`) and that no new width/min-width class forces overflow on small screens. Current header has an absolute submit button overlaying the input; dropdown's parent wrapper is the field itself, not the outer form, so its bounds match the input area as desired.

## Pass 3 — defect hunt / risks

1. Empty field queries are currently impossible at the API boundary (`q` min length 2), so trying to call `useCatalogDevices` or `useCatalogSuggestions` with `q: ''` will produce invalid requests or violate hook/cache expectations. Keep popular items local/static unless a separate endpoint is intentionally added.
2. `ready` currently controls `expanded` indirectly because `items=[]` whenever not ready. Introduce empty-state visibility without allowing stale previous query data to leak into an empty field after clear/debounce; branch explicitly on trimmed `value` and ensure pending previous data cannot render as popular matches.
3. Additive backend response fields can be rejected by current backend tests that assert exact keys (comparison API test above), while frontend Zod is currently strict by default. Update both contracts together.
4. This widget appears in multiple entry points with varied `suggestionsEnabled`, `filters`, and `onDeviceSelect` settings. Empty static suggestions must respect `suggestionsEnabled`; preserve auth gating for API-backed suggestions. Avoid surprising `/search` or logged-out behavior unless the requested contract intends it. The phrase “empty focused input” should be observed in the actual shared field scope.
5. Do not derive a model from a brand allowlist or prepend brand/model to the full canonical string (that duplicates model words). Use the structured model/brand to locate a matching span in canonical text, move that exact span ahead of the remaining canonical text, and fallback when it is absent. Preserve punctuation and qualifiers in the remainder.
6. Maintain listbox/combobox semantics. Each visible choice needs an option identity and `aria-selected`; Arrow Up/Down must traverse the presented options consistently, including the curated empty-state rows. Keyboard selection should route through existing handler.

## Pass 4 — polish / Terra regression coverage proposal

Recommended behavioral tests in `frontend/src/widgets/ProductSearch/ui/ProductSearchField.test.tsx` (shared header/home entry points where applicable):

- Focus an empty eligible field: assert a `Часто ищут` heading and the curated iPhone model queries (at minimum 15, 14, 13, 12); assert no catalog suggestion/device hook is enabled or invoked with an empty `q`.
- Click a popular row and separately select it with ArrowDown + Enter: assert the existing submit/navigation callback receives the literal model query (`/search?q=iPhone%2015`), the panel closes, and no fake device callback is used.
- Escape dismisses empty suggestions; blur closes them; focusing again reopens them; typing transitions to API-backed suggestions and does not show curated rows alongside results. Clearing a previously typed query while focused returns to curated rows without stale products.
- For a structured product fixture carrying both `canonical_name` and additive `display_name`, assert the row displays model first then part while Enter/click still invokes `onSelect(canonical_name)`. Include non-Apple and missing-model-span fixtures. Add a focused backend unit test around `ComparisonService.suggestions` with a mocked `AsyncSession`/result rows (no database or environment) to verify it emits `display_name` from structured values, moves the exact span without duplication, and falls back unchanged; retain the existing integration test's offer/filter coverage and update its exact-key assertion.
- Narrow-width behavior is best asserted in browser/manual gate G3 because jsdom does not perform layout: at desktop and mobile widths compare listbox bounding width to the input/wrapper and check viewport overflow; inspect the header and authorized home hosts. Manual evidence driver should record measured rectangles/screenshots in the gate.
- Preserve and rerun existing keyboard/device selection tests (`ProductSearchField.test.tsx`, `DeviceSearch.test.tsx`). Backend integration test should assert the new display field for a product with structured cluster relations and the fallback for an unstructured product; retain filter/active-offer constraints.
