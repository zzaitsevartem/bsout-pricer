# Сессия 6 — диагностика нагрузки и страницы поиска

Дата: 2026-10-23. Пользователь сообщил около 15 FPS, особенно на поиске, попросил проверку с агентами и явно разрешил отключить энергосбережение Chrome. Работа диагностическая: приложение не редактировалось, сервисы не перезапускались, нагрузочный тест не запускался, коммитов нет. Прочитан аудит 5, выполнены стартовые команды. Роли bscout_reader и bscout_coder использованы для двух ограниченных read-only проверок фронтенда и backend соответственно; стоимость/реальный billing не измерялись. Применён bscout-orchestrate, reader использовал vercel-react-best-practices.

Живые наблюдения:
- Docker stats (один короткий снимок): backend CPU 0.39%, RAM 240MiB; worker CPU 15.03%, RAM 532.2MiB; mail-worker 0.21%/152.7MiB; flower 0.11%/117.1MiB; beat 1.11%/101.8MiB; postgres 0.09%/143.7MiB; redis 0.76%/32.36MiB. Все контейнеры running, основные healthy. Процент Docker CPU нельзя читать как долю всех 10 ядер Mac.
- Mac: 10 logical CPU, 24GiB RAM. Два коротких top-снимка: idle 76.32% и 84.76%. 23G физической памяти занято, около 9G compressor; за интервал 0 swapins/swapouts. memory_pressure показал system-wide free 54%. Это не доказывает отсутствия всех проблем памяти, но CPU-упор/активный своп в этих снимках не виден.
- Next.js обслуживает :3000 в dev-режиме: main-app.js, hot-update и next-server v14.2.35. Текущий dev-сервер не сравнивался с production runtime.
- Открытая авторизованная главная: 213 DOM-узлов, canvas отсутствует. Тяжёлый Hero-canvas из публичной главной здесь не исполняется.
- Chrome показывал кнопку «Режим энергосбережения включен» и предупреждал об ограничении визуальных эффектов/плавной прокрутки. По явной просьбе пользователя нажато «Отключить», кнопка исчезла. Изменение проверено UI; улучшение FPS количественно не измерено.
- На /search около 2036 канонических товаров по текущему счётчику, выдача с пагинацией. При открытии DevTools обнаружены сохранённые настройки: Responsive 400px, Slow 4G, Disable cache; CPU No throttling. Эти настройки не изменялись. DevTools после осмотра закрыт.
- Live Metrics поиска: soft navigation LCP 0.24s, CLS 0, INP 24ms (одна показанная pointer interaction). Это не FPS и не полный профиль набора запроса/прокрутки. 15 FPS независимо не воспроизведены/не измерены.
- Снимок метрик: /private/tmp/bscout-search-performance.png. На мобильной ширине фильтры идут перед результатами, длинный список устройств занимает много экранов. Это реальная UX-проблема предыдущего вывода фильтров на мобильных.

Проверенные по коду возможности оптимизации:
1. SearchClient: debounce URL/API 350ms уже есть, но local text обновляет родителя при каждом символе; результаты/фильтры не изолированы от этих рендеров. Кандидат: локальный draft в отдельном SearchInput и отделение результатов. Влияние на FPS не измерено.
2. CatalogSearchView: каталог страницы, выборка 100 товаров для facets и до 20 отдельных офферов загружаются отдельно; также stores и tracking. Два списка по 20 строк дают визуальный шум. Кандидат: дополнительные офферы раскрывать по запросу, facets получать агрегированно; не уменьшать выборку facets без учёта потери вариантов.
3. SearchFilters: полный список устройств без ограничения/поиска; на мобильных перед результатами. Кандидат: компактная панель фильтров/раскрытие, ограничение высоты и поиск устройства.
4. TrackButton: запрос tracking общий и дедуплицируется React Query, HTTP-запроса на каждую строку НЕТ. Но каждая кнопка подписывается и ищет товар в общем списке. До 500 tracking записей загружаются до 5 последовательных страниц. Кандидат: одна подписка/Map для выдачи или batch статусов.
5. Старый /api/products: N+1 — отдельный StoreService.get_by_id на каждый оффер (products/controller/products.py:104–105; stores/service/store_service.py:19). Кандидат: join/пакетная загрузка магазинов. Это задержка API, не доказанная причина низкого FPS.
6. Catalog: два SQL запроса, без N+1; группировка офферов с DISTINCT и сортировка, при фильтрах повтор агрегации в count. Нужен EXPLAIN на реальной выборке перед SQL-оптимизацией. Trigram индексы предусмотрены миграциями; их наличие в текущей БД этой сессией не проверялось.
7. Search hooks не опрашивают API по таймеру; React Query staleTime 60s, focus refetch отключён. HeaderSearch не вызывает API автодополнения. Признаков бесконечного цикла запросов не найдено.

Не делать вывод «всё не оптимизировано»: пагинация, debounce и кеш уже есть. Следующий полезный шаг — профиль прокрутки/набора на поиске после отключения энергосбережения, отдельно от dev/Slow4G эффектов, затем ограниченные правки по подтверждённому узкому месту. Общая ёмкость платформы/число поддерживаемых пользователей не измерялись.
