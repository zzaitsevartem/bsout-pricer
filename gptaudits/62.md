## Проверенная текущая реализация

- Общая SQL-функция — `backend/src/modules/products/service/search_predicate.py:7–20,23–65`. Она сохраняет исходный token, строит OR по вариантам и AND между токенами. Раскладку EN↔RU и алиасы добавляет только при `fuzzy=True`; тот же флаг покрывает опечатки. API каталога и обычного поиска получает флаг через `is_fuzzy_enabled` (`backend/src/modules/products/controller/products.py:150–164`; `product_service.py:50–54`). Подсказки устройств используют предикат с default `fuzzy=False` (`comparison_service.py:213–250`), товарные suggestions прокидывают подписочный fuzzy-флаг (`:438–492`).
- Пример проверен по таблице, а не предположен: `ddjlt yf lheujv zpsrt` → `вводе на другом языке`.
- Отдельный каталоговый normalizer (`backend/src/modules/catalog/service/normalizer.py:152–165,184–204`) уже складывает `ё` в `е`, считает stem и `latin_key`/`token_variants`; extractor/matching использует эти варианты (`backend/src/modules/catalog/service/extractor.py:5,65–105,211–228`). SQL поиск их не вызывает.
- Хранимый текст офферов остаётся отдельной нормализацией: `backend/src/modules/parser/service/utils.py:15–20` приводит lower-case/пунктуацию без замены `ё`, а `parser_service.py:138–140,174–176` присваивает это `normalized_title`. `ProductService._normalize_query` только lower/strip (`product_service.py:12–15`).
- Единый SQL-предикат применяется к `StoreOffer.normalized_title`, `Product.canonical_name`, `Brand + DeviceAlias/Device` и suggestion search. Фронт сохраняет исходный ввод: поле отправляет query после 200 ms debounce в suggestions (`frontend/src/widgets/ProductSearch/ui/ProductSearchField.tsx:66–85`); основной search input debounce 350 ms (`frontend/src/app/search/_components/SearchInput.tsx:46–54`); URL/каталог несут исходное `q` и текущие filters (`SearchClient.tsx:41–55,81–95`, `CatalogSearchView.tsx:36–63`).
- Текущая модель/SKU path выделяет числовые и смешанные буквенно-цифровые tokens в отдельную regex-логику (`search_predicate.py:55–60`). Product list fuzzy sort использует raw query similarity либо выбранную цену (`product_service.py:78–89`); catalog использует `min_price_asc/desc` и product id tie-break (`comparison_service.py:426–432`). Фильтры должны оставаться авторитетными.
- Trigram индексы уже есть на `store_offers.normalized_title`, `products.canonical_name` и полях alias/synonym в `backend/alembic/versions/336d8cc4267a_core_offers_canonical_dictionaries_.py:229–248`. Query expansion может не требовать миграции, но column-side `replace()`/persisted-normalization может изменить plan; это нужно проверить до решения о backfill/index.
- Имеющиеся тесты дают переиспользуемые fixtures и негативные инварианты: `backend/tests/unit/test_search_predicate.py:10–31`, `backend/tests/unit/test_normalizer.py:16–59,95–132,166–198`, `backend/tests/integration/test_fuzzy_search.py:16–40`. В test-normalizer уже есть пары `айфон/iphone`, `лайт/lite`, `хуавей/huawei`, `камера/camera`; они относятся к entity matching, не SQL search.

## Библиотеки и решение

Библиотеки сверены только по первичным репозиториям/PyPI на 2026-11-06:

- [CyrTranslit upstream](https://github.com/opendatakosovo/cyrillic-transliteration) и [PyPI](https://pypi.org/project/cyrtranslit/) заявляют двустороннюю кириллическую/латинскую транслитерацию, поддержку русского и MIT; PyPI указывает релиз 1.2.0 от 2025-11-20. Это пригодный кандидат на сравнение, но наличие стандартной таблицы не решает вариативность пользовательского транслита.
- [AnyAscii upstream](https://github.com/anyascii/anyascii) и [PyPI](https://pypi.org/project/anyascii/) выполняют Unicode→ASCII посимвольно, context-free, релиз PyPI 0.3.3 с ISC. Одного его направления недостаточно для поиска латиницей по кириллическим строкам.
- [transliterate PyPI](https://pypi.org/project/transliterate/) содержит русский и reverse mode, но релиз 1.10.2 был 2018-09-17, лицензия GPL 2.0/LGPL 2.1.
- [Unidecode upstream](https://github.com/avian2/unidecode) описывает lossy, context-free ASCII transliteration и указывает GPL-2.0-or-later; это не поисковый словарь.

Рекомендация первого PR: без новой библиотеки; использовать локальную раскладочную таблицу, `latin_key`/`token_variants` и явные product aliases, ограничивая применение к коротким, mixed- и model tokens. Детерминированные варианты раскладки, `е/ё` и проверенного translit доступны всем планам; исправление fuzzy-опечаток остаётся Advanced-only. Это уточняет исторический fuzzy-раздел `docs/technical-specification.md:325–333`. Не путать transliteration с aliases, stemming и spellcheck. Для `е/ё` предпочтителен query-side regex-класс на существующем поле: PostgreSQL `pg_trgm` GIN поддерживает `~`/`~*`, но regex без извлекаемых триграмм может выродиться в полный index scan, поэтому проверить `EXPLAIN` и при плохом плане выбрать bounded fallback ([официальная документация `pg_trgm`](https://www.postgresql.org/docs/17/pgtrgm.html)). Миграцию/backfill не предполагать без evidence.

## Неопределённость и критерии завтра

Не обещать полную взаимозаменяемость русского транслита: написания `sh/shch`, `zh/j`, `kh/h`, `j/i`, `yo/e` не всегда однозначны. Не создавать варианты у любых латинских токенов: модельные хвосты `Pro`, `SE`, `XR`, `GT`, SKU/серии `SM-A525` и цифры должны оставаться разборчивыми. Query variants ограничить конечным бюджетом, сохранять исходную строку для UI/URL, AND по словам, исходные фильтры, сортировку и pagination.

Планируемые, но **не выполненные сегодня** проверки прописаны в `TASK.md`: положительный layout example, обе стороны `е/ё`, `plenka/shleyf/steklo`, смешанные query; отрицательные различения моделей, SKU, brands/quality; catalog/offers/facets/suggestions и фильтры; SQL count/budget/index path. Runtime-приёмка обязательна после тестов: backend image не имеет bind mount, поэтому Terra проверяет обновлённый контейнер/OpenAPI и authenticated read-only API на реальном товаре. UI/browser проверяется в разрешённой изолированной сессии; если она недоступна — явный follow-up, не completion.
