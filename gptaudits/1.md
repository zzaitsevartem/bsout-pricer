Порции по 50 URL фиксируются в PostgreSQL, затем offset в Redis:
`parser:checkpoint:{slug}:all`, TTL 7 дней. Квант примерно 600 секунд,
далее продолжение через Celery. Локальный worker concurrency=4,
PARSER_FULL_SYNC_ENABLED=true, браузер Profi включён, город Ставрополь.
Расписание Celery UTC: полный обход 03:00 UTC = 06:00 МСК;
обновление цен 07:30/13:30/19:30 UTC касается отслеживаемых офферов.

Локальный запуск из корня:
`docker compose up -d postgres redis backend worker beat`.
Ручной запуск: Админка → Парсеры → Полный обход каталога → нужный магазин/все;
пустой раздел означает весь sitemap. Backend без worker ничего не парсит.
Для работы нужны Docker, интернет и отсутствие сна компьютера.
Перед остановкой: `docker compose stop -t 900 worker beat backend`, дождаться.
Redis в локальном compose НЕ имеет постоянного тома. `docker compose down`
и пересоздание Redis могут потерять очередь/checkpoint; PostgreSQL использует pgdata.
Жёсткое прерывание может оставить parser-lock до 6 часов и статус до 24 часов;
автоматическое восстановление после произвольного сбоя не считается доказанным.
Не удалять lock без проверки отсутствия живой задачи.

## Причина → следствие → действие

1. В работающем worker `settings.parser_full_sync_enabled=False`.
   `src/worker.py::_sync_catalog` при этом возвращает `disabled` до вызова парсеров.
   Следствие: наличие beat и здорового worker само по себе не запускает наполнение.
   В начале проверки Celery: очередь `celery` — 0, active — пусто у обоих воркеров;
   Redis `SCAN parser:*` — пусто. В логах `sync_prices` — `candidates: 0`:
   эта задача обновляет только отслеживаемые офферы, а `tracked_products` содержит 0 строк.
   Выполнен явный запуск четырёх `run_parser` через брокер Celery;
   в локальном Compose для worker включён флаг ночного обхода по умолчанию.
   Ночная задача ставит отдельные `full_sync=True` задачи всех зарегистрированных
   парсеров без ограничения количества карточек. Полный обход сохраняет порции
   и продолжает работу с контрольной точки; ограничение первыми 500 снято.

2. Profi (`https://siriust.ru/sitemap.xml`) возвращает HTTP 503.
   Уточнение прямой проверкой: главная, sitemap, robots.txt и `/zapchasti/`
   возвращают HTML с title «Проверка безопасности...» и JavaScript проверки браузера.
   Это блокировка HTTP-клиента защитой сайта, а не доказанный простой магазина.
   Диагностический прогон и повторный Celery-прогон воспроизвели три неуспешные попытки.
   Следствие: список URL пуст, записано 0 офферов. Обход блокировки не предпринимался.
   До исправления `ParserService.run_one` возвращал `status: done` даже при этих ошибках.
   Теперь возвращает `error` при нуле записей с ошибками, `partial` при записях с ошибками;
   ошибки включены в результат задачи. Добавлен регрессионный unit-тест.

## Полнота и ограничения

Сбор sitemap без лимита обнаружил TGSM — 71 799 URL, Liberti — 9 260,
Divizion — 10 691; Profi — 0 из-за HTTP 503.
Прогон с limit=200 не является полным обходом магазинов.
Раньше `update_catalog` сначала собирал весь результат в памяти и только затем
`ParserService.run_one` записывал его в БД. Для полных обходов это исправлено:
новые `catalog_urls`/`parse_catalog_batch` у всех четырёх парсеров и
`ParserService._run_full_catalog` сохраняют и сопоставляют каждые 50 URL,
фиксируют транзакцию, затем сохраняют следующий offset в Redis на 7 дней.
Сначала commit БД, затем checkpoint: повтор порции после сбоя идемпотентен по
существующему уникальному `(store_id, source_sku)`.
`run_parser` и `sync_catalog` имеют hard time limit 21 600 секунд.
У TGSM concurrency=2 и REQUEST_DELAY=1 секунда: одних задержек на 71 799 URL
требуется минимум около 35 900 секунд. Поэтому после порции и примерно 600 секунд
работы задача ставит продолжение в очередь и освобождает worker. Это не ограничение
общего числа карточек: следующий запуск читает сохранённый список URL и offset.
Ограниченный `update_catalog(limit=...)` сохранён для ручных диагностических запусков.
Запись порций защищена транзакционной advisory-блокировкой PostgreSQL, чтобы
параллельные магазины не создавали одну каноническую карточку одновременно.
Локальный worker переведён на concurrency=3, почтовый worker не менялся.
Неполнота сопоставления, фильтрация разделов Divizion, HTTP 404/503,
отсутствующий GreenSpark и короткие fuzzy-запросы остаются незакрытыми.

## Ошибочное объединение HTC Desire

По запросу пользователя проверены реальные `products` и `store_offers`.

`extractor._best_match` выбрал известный префикс `htc desire`, а конкретных модификаций
не было в справочнике (из семейства существовали только Desire, 300 и 310).

- Добавлены модели 400, 500, 516, 816, V, X, HD и наблюдаемые аппаратные обозначения.
- Неизвестный числовой/модельный суффикс не подменяется родительской моделью;
  обозначения `45 pin` и `1-я категория` учитываются отдельно от номера модели.

  подставляет Honor X6 из-за общего алиаса `x6`.
- В каноническое название включён цвет, который уже входил в ключ группировки.

  («1-я категория»), без приравнивания её к оригиналу/OEM.
- Пересопоставление сбрасывает прежний автоматический `product_id`, если новая
  модель больше не распознана; ручные `manual` и `rejected` решения сохраняются.
