### [MEDIUM] Детект кражи refresh-токена (reuse detection) не отзывает access-токены: до 15 минут полного доступа после срабатывания защиты

**Где:** `backend/src/modules/auth/service/token_service.py:226-238 (_load_usable_token) и 191-199 (revoke_family)`

**Атака:** Атакующий украл refresh-токен жертвы (XSS/localStorage/лог прокси) и первым делает POST /api/auth/refresh — получает свежую пару access+refresh. Клиент жертвы позже приходит со старым (уже ротированным) refresh → срабатывает reuse detection: revoke_family() гасит всё семейство refresh-токенов. НО invalidate_access_tokens() при этом не вызывается (в отличие от logout, revoke_session:274, и смены/сброса пароля, revoke_all_for_user:212-213). Access-токен атакующего продолжает работать весь остаток TTL (до 15 мин): чтение /api/users/me и /api/payment/history (PII, история платежей и суммы), отмена подписки жертвы POST /api/payment/cancel, создание платежей, привязка соц-идентичностей. Смысл reuse detection — «убить сессию при краже» — выполняется только наполовину: жертва и система думают, что сессия убита, а она жива.

**Доказательство:** Подтверждено запуском против живого API (порт 8123):
 attacker access works: 200
 victim refresh -> theft detection: 401 'Refresh token reuse detected, session revoked'
 attacker REFRESH after detection: 401
 attacker ACCESS after detection : 200   <-- сессия НЕ убита
   still reads /api/payment/history: 200
Для сравнения, те же проверки на logout / смене пароля / сбросе пароля дают 401 на access сразу.

**Исправление:** В _load_usable_token в ветке reuse (`if stored.replaced_by_jti is not None`) вызывать `await invalidate_access_tokens(stored.user_id)` до `db.commit()` — либо перевести ветку на `revoke_all_for_user(db, stored.user_id, REASON_REUSE)`, который уже делает и то и другое. Логично также разослать уведомление на почту, как это сделано при смене пароля.


### [MEDIUM] Тайминг-оракул перечисления аккаунтов на POST /api/auth/login (223 мс против 6 мс, разница в 37 раз)

**Где:** `backend/src/modules/auth/service/auth.py:143-149 (authenticate_user)`

**Атака:** `if user is None or not verify_password(...)` — Python замыкает `or`, поэтому для несуществующего email bcrypt вообще не считается. Ответ одинаковый (401 «Invalid email or password»), но время отличается на два порядка: существующий аккаунт ~223 мс (bcrypt cost 12), несуществующий ~6 мс. Атакующий проверяет списки email из чужих утечек и получает точный список зарегистрированных клиентов BScout — это база для целевого фишинга («ваша подписка BScout истекает») и для credential stuffing. Отдельно отмечу: на /api/auth/password-reset/request этот же оракул закрыт (5.0 мс против 5.7 мс — фикс держится), то есть /login просто забыли. Скорость ограничена auth-бакетом 10 запросов/300 с на IP, что замедляет, но не устраняет перебор (≈2880 проверок в сутки с одного IP, тривиально масштабируется по IP).

**Доказательство:** 12 замеров по каждому варианту против живого API:
 existing account, wrong pw : median 223.5 ms
 non-existing account       : median 6.0 ms
 ratio = 37.5x
Контроль (уже починенный эндпоинт): password-reset/request — existing 5.0 ms | unknown 5.7 ms.

**Исправление:** В authenticate_user всегда выполнять bcrypt: при user is None сверять пароль с заранее посчитанным фиктивным хэшем (`_DUMMY_HASH = pwd_context.hash(secrets.token_urlsafe(32))` на уровне модуля), затем возвращать None. Порядок: сначала посчитать verify, потом решать. То же применимо к пользователям с unusable-password (VK-аккаунты) — там verify отрабатывает и время совпадает, отдельного действия не требуется.


### [LOW] Denylist access-токенов живёт только в Redis, fail-open: перезапуск/вытеснение Redis воскрешает все отозванные access-токены

**Где:** `backend/src/modules/auth/service/token_service.py:68-137 (invalidate_access_tokens / access_tokens_invalid_before / access_token_is_invalidated)`

**Атака:** Отзыв access-токена реализован одним ключом `auth:invalidate:<user_id>` c TTL 15 мин. Тот же эффект даёт потеря ключа: в docker-compose.yml redis:7-alpine поднят без volume и без appendonly, с `restart: unless-stopped`, maxmemory-policy не задан. Снаружи спровоцировать напрямую нельзя (кэш поиска в Redis сейчас не пишется, безлимитного роста ключей от пользовательского ввода я не нашёл), поэтому это ops-риск, а не удалённая атака.

**Доказательство:** Подтверждено запуском: после logout access → 401; ключ в Redis присутствует (`auth:invalidate:16`); после `redis-cli del auth:invalidate:16` тот же access-токен снова даёт 200 на /api/users/me.

**Исправление:** Дублировать отметку отзыва в Postgres (например, колонка users.tokens_invalid_before, обновляемая в той же транзакции, что и revoke_all_for_user) и сверять её в get_current_user; Redis оставить как кэш. Минимальный вариант: включить persistence у Redis (appendonly + volume) и задать `maxmemory-policy noeviction`, а при REDIS_ERRORS в access_tokens_invalid_before делать fail-closed (401) вместо fail-open.

### [LOW] Reset-токен работает как неограниченный оракул «является ли эта строка текущим паролем», не сгорая при попытке

**Где:** `backend/src/modules/auth/service/password_service.py:237-249 (confirm_password_reset)`

**Атака:** В confirm_password_reset проверка `verify_password(new_password, user.password_hash)` → SamePasswordError выполняется ДО _claim_reset_token(), поэтому при совпадении токен не помечается использованным. Держатель перехваченного reset-токена (или сам владелец ссылки из чужого почтового ящика/логов прокси) может неограниченно долго перебирать кандидатов: ответ 400 «Новый пароль должен отличаться от текущего.» означает «угадал», любой другой ответ — «не угадал», токен остаётся живым весь свой час. Практическая ценность — узнать пароль жертвы для повторного использования на других сайтах, не спалив сброс (жертва не получит письмо «пароль изменён»). Скорость ограничена auth-бакетом 10 запросов/300 с на IP.

**Доказательство:** Подтверждено запуском: guess == current password → 400 «Новый пароль должен отличаться от текущего.»; повтор того же запроса → снова 400 (токен жив); затем реальный сброс тем же токеном → 200.

**Исправление:** Сначала атомарно забирать токен (_claim_reset_token), и только потом сравнивать новый пароль с текущим — тогда одна попытка = один сожжённый токен. Либо возвращать на этот случай тот же обобщённый ответ 200/400, что и при успехе, не раскрывая совпадение.


### [INFO] decode_token не требует обязательного exp/iat: токен без exp не истекает никогда

**Где:** `backend/src/modules/auth/service/auth.py:68-73`

**Атака:** jwt.decode вызывается без options={'require': ['exp','iat','sub','type']}. Проверено запуском: подписанный правильным секретом токен без exp и без iat принимается и даёт 200 на /api/users/me бессрочно. Эксплуатации без утечки JWT_SECRET_KEY нет (все пути выдачи токенов ставят exp), поэтому это defense-in-depth: при любой компрометации/ротации секрета или ошибке в будущем коде выдачи такой токен станет вечным, а ещё он обходит denylist-логику иначе (access_token_issued_at вернёт None → токен считается отозванным только если denylist-ключ существует).

**Доказательство:** Тест против живого API: [no exp, valid sig] 200, [no exp no iat] 200. Все остальные варианты отбиты: alg=none 401, чужой секрет 401, подмена HS256→HS512 401, refresh как Bearer 401, access в /auth/refresh 401, просроченный 401, без claim type 401, claim is_admin:true → /api/admin/stats 403.

**Исправление:** jwt.decode(..., algorithms=[settings.jwt_algorithm], options={'require': ['exp', 'iat', 'sub'], 'verify_exp': True}) и явная проверка наличия type.

### [LOW] Неэкранированные wildcards % и _ в ILIKE-поиске (обход/переполнение фильтра)

**Атака:** Пользовательский запрос q подставляется как значение bound-параметра в StoreOffer.normalized_title.ilike(f"%{normalized}%") без экранирования спецсимволов LIKE. Запрос q=%25 (один символ '%') на нечётком-выключенном тарифе (basic) возвращает ВСЕ 308 офферов (ILIKE '%%%' = любая строка); q=_ тоже 308; q=%iphone% (=%25iphone%25) даёт 116 вместо точного совпадения. Т.е. пользователь может выбрать пустой/wildcard-запрос и получить всю выдачу либо переопределить логику подстроки. **Доказательство:** backend/src/modules/products/service/product_service.py:36 и :123; comparison_service.py:109. Прогон API: q=%25 -> total=308, q=_ -> total=308, q=%25iphone%25 -> total=116 (на пользователе с планом basic, fuzzy off).

**Исправление:** Экранировать % _ \\ в пользовательском вводе перед подстановкой в LIKE-паттерн и использовать .ilike(pattern, escape='\\'); либо для fuzzy-независимого поиска использовать полнотекст/сравнение. Как минимум — экранирование, чтобы q не мог содержать управляющие wildcards.

Утечки стек-трейса/SQL нет (тело ответа — только 'Internal Server Error'), но это необработанное исключение. Кроме того любые большие валидные page форсируют большие OFFSET-сканы. Затрагивает /api/products, /api/products/catalog, /api/tracking, /api/tracking notifications, /api/admin/* списки — везде page=Query(ge=1) без le.

**Доказательство:** backend/src/modules/products/controller/products.py:61 'page: int = Query(default=1, ge=1)'. Прогон: page=100000000000000000000 -> тело ответа 'Internal Server Error' (HTTP 500).

**Исправление:** Добавить разумную верхнюю границу page (например le=10000) во все контроллеры, либо перейти на keyset-пагинацию. Обернуть слой сервиса, чтобы недопустимый offset давал 400/422, а не 500.


### [LOW] Нет ограничения на размер тела HTTP-запроса (буферизация в память)

**Атака:** Приложение не задаёт лимит размера тела (в main.py только RateLimitMiddleware + CORS). POST /api/auth/register с JSON-телом 50 МБ полностью считывается в память и парсится, прежде чем Pydantic отклонит пароль (ответ 422 за 0.22с). Это вектор memory-DoS: злоумышленник шлёт крупные тела. Частично смягчено auth-лимитом (10 запросов/5мин на IP на путях /api/auth/*), но 10×50МБ за окно на IP всё равно возможно; прочие POST-эндпоинты требуют аутентификации (глоб. лимит 120/60с).

**Доказательство:** Прогон: тело 50000049 байт на /api/auth/register -> HTTP 422 за 0.217с (тело принято и распарсено целиком). В main.py нет middleware ограничения размера тела.

**Исправление:** Ввести middleware/проверку Content-Length с разумным потолком (например 1–2 МБ) до чтения тела, либо ограничить на уровне обратного прокси (nginx client_max_body_size). Для admin /api/admin/offers/import (rows: list[Any]=Body(...)) добавить max_items.


### [INFO] debug=True по умолчанию в config.py -> echo SQL с хешами и толерантность к слабому JWT-секрету

**Атака:** Settings.debug по умолчанию True. database.py создаёт движок с echo=settings.debug, поэтому при DEBUG=true SQL-лог печатает значения bound-параметров: password_hash (bcrypt) и token_hash (sha256 токенов сброса/верификации/refresh jti) — это хеши, не плейнтекст, но всё же чувствительные данные в логах. Дополнительно validate_security_settings при debug=True лишь ПРЕДУПРЕЖДАЕТ (не отказывается стартовать) о дефолтном/коротком jwt_secret_key. Развёртывание, забывшее выставить DEBUG=false, работает в insecure-by-default режиме. Смягчено тем, что .env.example и backend/.env ставят DEBUG=false.

**Доказательство:** backend/src/config.py: 'debug: bool = True'; database.py:17 'echo=settings.debug'; security.py: при debug проблемы лишь логируются как warning. В локальном логе видны строки INSERT/SELECT users с '$2b$12$...' (bcrypt) и token_hash.

**Исправление:** Сделать debug: bool = False по умолчанию. echo движка не завязывать напрямую на debug (отдельный флаг sql_echo, по умолчанию False). Оставить отказ старта при слабом секрете независимо от debug в проде.


**Вывод угла:** УГОЛ 3 (инъекции, утечки, DoS). SQL-инъекций НЕ найдено: весь доступ к БД — SQLAlchemy Core с bound-параметрами, sort_by берётся из whitelist-словаря с безопасным дефолтом, сырой SQL есть только в alembic-миграциях со статическими константами. Утечек секретов в логах/ответах нет: токены, ссылки сброса/верификации и пароли не логируются, стек-трейсы/SQL/пути ФС не отдаются клиенту даже на 500, FastAPI не в debug. CORS корректно ограничен localhost:3000. Найдено 5 второстепенных проблем (все low/info), подтверждённых запуском API против БД bscout: (1) N+1 в /api/products — 100 отдельных SELECT stores на страницу в 100 офферов (усиление нагрузки, тривиально батчится); (2) неэкранированные wildcards % и _ в ILIKE — q=% возвращает всю выдачу (обход/переполнение фильтра, не SQLi, не ReDoS); (3) параметр page без верхней границы -> OFFSET-переполнение bigint даёт необработанный 500 и большие OF


## Что исправлено сразу после аудита

- **[MEDIUM] Детект кражи refresh-токена не гасил access-токены** — украденная сессия жила ещё 15 минут после срабатывания защиты, то есть защита работала наполовину именно там, где нужнее всего. Исправлено, закреплено тестом `test_reuse_detection_also_kills_access_tokens`.
- **[MEDIUM] Тайминг-оракул на входе** — 223 мс против 6 мс выдавали существование аккаунта по секундомеру. Добавлено вычисление хэша-пустышки для несуществующего пользователя; тест `test_login_timing_does_not_reveal_existing_accounts` требует разницы менее чем в 3 раза.
- **[INFO] `debug=True` по умолчанию** — защита от дефолтного `JWT_SECRET_KEY` молчала, если `DEBUG` не задан явно, а SQL-эхо писало хэши паролей в лог. Дефолт изменён на `False`: безопасное поведение теперь по умолчанию, а не по настройке.
- **[INFO] Токен без `exp` жил вечно** — `decode_token` теперь требует `exp` обязательно.
- **[LOW] `page` без верхней границы** давал необработанный 500 через переполнение OFFSET — проставлен предел.

## Осталось незакрытым (требует решений владельца)

- **Подпись вебхука ЮKassa — заглушка.** Настоящий алгоритм провайдера не реализован. Вебхук закрыт по умолчанию (503 без секрета), но перед подключением мерчанта подпись обязательно заменить.
- **`python-jose` заброшена и имеет известные CVE.** В текущей конфигурации не эксплуатируется (алгоритм фиксирован), но библиотеку стоит заменить на `pyjwt`.
- **Denylist access-токенов живёт только в Redis.** Перезапуск Redis воскрешает отозванные токены на остаток их жизни (до 15 минут). Надёжнее — колонка `users.tokens_valid_after`.
- **Энумерация аккаунтов при регистрации** по коду 409. Полное устранение требует смены контракта на «проверьте почту».
- **Перехваченный набор Телеграм-виджета** внутри окна 60 секунд может быть применён другим аккаунтом — свойство самого виджета. Правильное решение — перейти на привязку через deep-link бота, которая заодно даёт `chat_id`, необходимый для отправки уведомлений.
- **Нет ограничения на размер тела запроса** — задаётся на уровне обратного прокси при деплое (Блок 15).
