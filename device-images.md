# Задание: локальные showcase-фото устройств на белом фоне

Подготовь и внедри масштабируемое наполнение страниц устройств фотографиями самих устройств на белом фоне. До реализации проверь актуальный код, рабочее дерево, план и инфраструктуру хранения/раздачи. Этот файл задаёт контракт реализации, но не разрешает платные сервисы, покупку лицензий или несвязанные изменения.

## Проверенные исходные факты и перепроверка

- По `gptaudits/54.md`, страницы `/devices/[model_key]` уже показывают фото устройства с атрибуцией и поддерживают галерею/fallback. Исторически данные импортировались из `backend/data/device_metadata.json` через `backend/src/modules/catalog/service/device_metadata.py`; аудит упоминает `url`, `source_name`, `source_url`, `license`, `attribution`. Перед работой подтверди актуальные контракты.
- Аудит54 зафиксировал срез: 449 устройств, фото у 2. Это не текущая гарантия. Пересчитай актуальное покрытие безопасным read-only способом и укажи условия подсчёта. Не называй частичное заполнение полным.
- Текущий reader подтвердил: metadata JSON в `backend/src/modules/catalog/model/catalog.py:38-45`, сериализация `backend/src/modules/catalog/schema/device.py:4-10,20-32`; `GET /api/devices/{model_key}` в `backend/src/modules/catalog/controller/devices.py:13-32` делает DB select с `selectinload` Brand/Aliases, без Redis. Frontend: `frontend/src/models/device/service.ts:3-8`, `hooks.ts:3-9`; `DeviceOverview.tsx:31-44` передаёт `image.url` прямо в `NextImage unoptimized`, атрибуция в `:66-73`. Сейчас принятые фото загружаются браузером с third-party origin; app не хранит и не раздаёт image bytes.
- Reader не подтвердил browser HTTP cache headers, отдельный device image volume/origin, постоянство `frontend/public` после пересборки или готовую object-storage абстракцию. Не заявляй это существующим поведением. Проверь актуальные compose/nginx/standalone конфигурации и deployment пути перед выбором хранения; требуется явный persistent shared volume + static route либо реально существующее object storage. Axios/Next rewrite проксирует JSON, не изображения. Не считай in-memory TanStack Query JSON cache браузерным HTTP image cache.
- В начале работы прочитай актуальные `docs/plan/MASTERPLAN.md`, последний нумерованный `gptaudits/N.md`, вложенные `AGENTS.md`, `docs/technical-specification.md` и task-relevant skills. MASTERPLAN — единственный live plan; этот файл — задание, не параллельный TODO.

## Цель и визуальное качество

Для каждой подходящей модели каталога постепенно обеспечить хотя бы одно проверенное showcase-изображение самого устройства: точная модель/вариант, товарный ракурс, чистый белый или прозрачный фон, центрирование и достаточное разрешение. Сначала исследуй доступные источники и проведи визуальный пилот примерно на 12 моделях как минимум трёх брендов/типов устройств, включая неоднозначные соседние варианты. Это размер выборки для проверки процесса, не обещание доступности 12 подходящих фото: недоступные/неподтверждённые модели отклоняй и учитывай с причиной. Только после подтверждения доступности, прав и качества выбирай масштабируемый источник/процесс.

Предпочитай материалы производителя или дистрибьютора с явными условиями повторного использования. Wikimedia Commons — проверяемый fallback, но не обещание покрытия или студийного качества. MediaWiki Imageinfo (`https://www.mediawiki.org/wiki/API:Imageinfo`) и Wikidata P18 — лишь точки исследования, не гарантия качества, лицензии, доступа или точного совпадения. Поиск Google и другие поисковики допустимы для обнаружения возможного источника, но поисковый thumbnail/результат не является источником файла или доказательством лицензии: проверяй исходную страницу и права. Не загружай вслепую изображения из поиска, случайных магазинов/объявлений; не обходи 403/robots/ограничения и не скрейпь вопреки условиям сайта. Не выдумывай права, автора, лицензию, модель или источник. Не подключай платный сервис, аккаунт/API-ключ или платную обработку без отдельного явного выбора пользователя.

Сгенерированное изображение устройства, фото соседней модели/варианта, фото запчасти, телефона в руке или lifestyle-кадр не является принятым default showcase. Старые Commons изображения сохраняются как fallback; учитывай их отдельно от фото, соответствующих новому визуальному стандарту.

## Контракт, хранение и доставка

- Проверь deployment, постоянные тома, резервное копирование, nginx/static маршруты и наличие object-storage абстракции. Выбери наименьшее изменение, совместимое с реальным развёртыванием. Не предполагай CDN, бакет или готовый image API. Не дублируй один набор в `frontend/public` и backend без доказанной нужды.
- Предпочтительный вариант для проверки: хранить собственные подготовленные файлы на подтверждённом persistent disk/shared volume, URL — в текущем DB JSON, отдавать через Nginx с HTTP cache. Сравни с уже существующим object storage, если он реально есть. Это снижает лишнюю работу приложения/БД по передаче bytes, но не обнуляет нагрузку: disk/network traffic остаются, offline import требует CPU; не обещай нулевую нагрузку.
- Бинарные файлы храни вне БД/Redis на подтверждённом persistent storage или через подтверждённое object storage. В БД храни стабильный локальный public URL/путь и provenance: точный `model_key`/устройство, исходный URL/ID, источник, автор, лицензия/условия, дата получения, source/derivative asset, версия обработки и статус проверки. Сохраняй требуемую атрибуцию и для производной копии.
- Сначала проверь, покрывают ли существующие JSON-поля и API metadata contract. Не добавляй migration/schema без необходимости; если необходима — обоснуй и сделай минимально совместимой.
- Раздавай готовые файлы через подтверждённый static/object-storage route с корректными MIME и HTTP cache headers; используй стабильные versioned или content-hashed URL. Не скачивай, не ресайзь и не проксируй исходник при запросе страницы. Проверь доступность после restart/rebuild, не зависящую от временного слоя контейнера.
- Определи cache invalidation через versioned URL и/или корректные TTL/validators; DB URL/metadata могут по-прежнему читаться при открытии страницы — не заявляй «нулевой DB load» или вечный кэш. Текущий `frontend/src/shared/config/query-client.ts` задаёт JSON query `staleTime` 60 секунд, а device images идут браузером напрямую с третьей стороны; не путай это с HTTP image cache.
- Redis не использовать для image bytes. Кэшировать JSON деталей только если измерения показывают пользу и текущая архитектура это поддерживает. Отдельно укажи DB/API запросы: локальное изображение само по себе не отменяет чтения данных устройства.

## Получение, проверка и обработка

Реализуй воспроизводимый, resumable и идемпотентный поток получения/проверки/импорта с dry-run, ограниченными пакетами, отчётом на каждую модель и причину пропуска, повтором без дублей и безопасным продолжением после сбоя. Не перезаписывай утверждённый asset пустыми, неподтверждёнными или ухудшенными данными. Импорт не создаёт устройства и не меняет связи товаров/предложений или product images.

По текущему reader, импортёр добавляет `images` только если у устройства их ещё нет, а `DeviceOverview` отображает первым `images[0]`. Поэтому явно поддержи reviewed promotion/замену основного фото для точного `model_key`, не теряя допустимые gallery entries/их provenance; конвертируй approved external URL в локальный URL даже если старый массив уже непуст. Повтор не создаёт дубликаты. Ошибка загрузки/валидации не заменяет работающий asset битой ссылкой, пустым значением или непроверенным фото.

Применяй allowlist источников, HTTPS там, где поддерживается, timeouts, лимит размера ответа и разрешения, проверку фактического MIME/декодирования, ограниченную concurrency ориентировочно 2–4 и защиту от SSRF/редиректов во внутренние адреса. Не доверяй только расширению или Content-Type; не загружай активный SVG как растровое изображение без явной безопасной обработки.

Для готового белого/прозрачного исходника начни с детерминированного contain без обрезки корпуса, белой квадратной подложки и WebP около 600×600, первоначально quality 80–85. Настрой по визуальному пилоту и размерам. Мягкая цель 30–100 KB на файл; это ориентир, не повод портить картинку. Установи обоснованный hard limit и отчитай исключения. Сохрани разрешённый оригинал/восстановимый исходник отдельно, если оправдано правами и объёмом; в любом случае оставь provenance и воспроизводимый способ обработки. Проверь, что устройство целиком видно без артефактов.

Удаление фона допустимо только как опциональная offline-обработка лицензированных оригиналов после пилота. Не отправляй изображения внешнему сервису и не используй платную обработку без явного выбора пользователя. Сохраняй оригинал и проверяй результат вручную, не принимая стёртые/галлюцинированные детали.

## Производительность

Начальный объём — один основной showcase asset на модель, примерно 600×600 WebP. Дополнительную галерею для нового набора не собирай как обязательный этап: это увеличивает поиск, проверку прав и загрузку. Сохрани уже существующие допустимые gallery entries. Используй lazy loading ниже первого экрана, разумные responsive `sizes`/dimensions и fallback для старых внешних записей/ошибок. Не нарушай лицензионную атрибуцию.

Измерь холодную загрузку: число image requests, байты файла, response cache headers и запросы при повторном reload. Кэш должен подтверждаться HTTP ответами браузеру/CDN/nginx, не Redis blob. По возможности отдельно зафиксируй API/DB и image delivery. Только пример для планирования: 449 × 80 KB ≈ 35 MB производных; фактический объём измерить, оригиналы/галереи считать отдельно. Это не обещание покрытия/бюджета.

## Работа и разрешённый объём

- Используй роли/профили явно, сохраняя доступные настройки:
  - `bscout_reader` на GPT-6 Luna medium: исследование источников, лицензий и неоднозначных соответствий. Не пытайся менять фиксированный профиль на low.
  - Рутинная работа — один worker на GPT-6 Luna low через нативную возможность worker/default override, если доступна: manifest, сверка, безопасная загрузка и preprocessing bounded batches. Один worker/script обслуживает пакеты; не назначай отдельного агента на каждую модель. Не утверждай, что конкретный override доступен, если runtime его не предоставляет.
  - Существующий `bscout_coder` GPT-6.1 Sol low допустим только если нужна нетривиальная кодовая/инфраструктурная работа; он не обязателен для рутинной сверки или обработки файлов.
  - Основной orchestrator на текущей модели отвечает за контракт и assignment, принимает решения, интегрирует результат и независимо проверяет пилот/неоднозначные соответствия/выборку. Он не должен выполнять рутинную пакетную работу или забирать на себя большой объём кода.
- Для возможной работы coder-а назначай ownership без пересечений: importer/metadata и утилита обработки/её тесты — одна область; compose/nginx persistence/static route — отдельная область, поручать тому же coder-у последовательно, если инфраструктурная часть тесно связана. `DeviceOverview`/schema/API менять только при строгой необходимости и с отдельным явным файлом-владельцем; не допускай двух параллельных writers в один файл.
- До запуска writers уточни и зафиксируй в MASTERPLAN непересекающееся владение. Исходная карта ниже — предлагаемые области, а не заявление, что новые файлы уже существуют:

| Владелец | Файлы/область |
|---|---|
| Luna reader medium | Только чтение; актуальный каталог моделей, источники и deployment |
| Luna worker low | Новый `backend/scripts/device_images/` для пакетной подготовки и manifest; подготовленные assets в выбранном постоянном хранилище, вне Git |
| Coder при необходимости | `backend/src/modules/catalog/service/device_metadata.py`, `backend/data/device_metadata.json`, необходимые catalog schemas/tests; `deploy/nginx/` и compose-файлы только для подтверждённого static route/persistent volume |
| Тот же coder, последовательно | `frontend/src/app/devices/[model_key]/DeviceOverview.tsx` и `frontend/src/models/device/` только если текущего контракта недостаточно; соответствующие тесты |
| Основной агент | Независимая проверка результатов, визуальная приёмка и отчёт |

- Не строй обязательную агентскую цепочку, не используй Astra/Terra и не эскалируй автоматически. Не заявляй точные цены/экономию: реальные тарифы и доступность runtime-профилей не проверены. Если выбранный профиль недоступен, сообщи об этом; не подменяй его более дорогой моделью без согласования.
- Сохраняй unrelated dirty worktree. Не читай/меняй реальные `.env`, не устанавливай зависимости и не перезапускай существующий сервер/браузер без нужды. Изолируй DB/Redis integration checks, если они нужны; не очищай пользовательские сервисы. Не коммить без отдельного запроса.
- Меняй только device images, связанный импорт/раздачу и необходимые API/UI контракты/тесты. Не меняй товары, предложения, парсеры, product images, платежи, поиск, тарифы или другие страницы.

## Критерии приёмки

1. До массовой загрузки готов визуально проверенный многобрендовый пилот, включая неоднозначные варианты; описаны источники, права, coverage и отклонения. Нет фото соседней модели.
2. Bounded процесс расширяет охват всех подходящих существующих моделей настолько, насколько позволяют проверенные источники. Финальный отчёт отдельно показывает актуальное количество устройств, eligible/processed/accepted showcase, fallback-only, missing/rejected/blocked с точными причинами, реальные bytes и storage footprint. Непокрытые модели остаются явно непокрытыми.
3. Каждый принятый asset показывает правильную модель целиком на белом/прозрачном фоне и имеет проверяемые права/provenance/атрибуцию. Orchestrator независимо просматривает весь пилот, неоднозначные/автоматически сопоставленные варианты и случайную выборку массового набора; сообщает размер выборки и исправления.
4. Импорт идемпотентен, возобновляем и поддерживает dry-run; плохие/пустые данные не затирают утверждённые; товары/предложения неизменны.
5. Локальные assets доступны после restart/rebuild из подтверждённого persistent storage, с корректным MIME/cache headers; принятые images не требуют запроса к source origin. Рабочие Commons/error fallbacks сохранены.
6. Проверены desktop и mobile: точная модель, белый фон, contain без обрезки, размеры/галерея, fallback/атрибуция, отсутствие заметного layout shift/горизонтального overflow. Network показывает реальные число запросов и bytes.
7. Добавлены нужные регрессионные тесты, выполнены пропорциональные проверки; handoff перечисляет точные команды, результаты и пропуски. Не заявляй live billing, coverage или browser/storage acceptance без измерения.
