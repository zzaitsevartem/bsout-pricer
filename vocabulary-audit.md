# Задание на 2026-11-07: варианты написания в поиске BScout

## Цель

Научить текстовый поиск находить каталог и офферы, когда пользователь вводит русское слово в английской раскладке, пишет `е` вместо `ё` или вводит русское слово латиницей (например, `plenka` → «пленка»). Сохранить исходный текст пользователя в строке поиска и URL. До изменения кода подтвердить контракт ниже и выбрать отдельную политику для трёх преобразований: раскладки, `е/ё`, транслитерации.

Пример раскладки разобран по фактической таблице QWERTY→ЙЦУКЕН из `backend/src/modules/products/service/search_predicate.py`: `ddjlt yf lheujv zpsrt` → `вводе на другом языке`. Не трактовать пример как произвольную опечатку.

## Что уже есть

- `search_predicate.py` строит для каждого слова OR из исходного слова и вариантов, а затем AND между словами. Варианты раскладки, перекрёстные алиасы и fuzzy-опечатки сейчас добавляются только при `fuzzy=True` (`search_terms`, строки 23–46). Параметр fuzzy включается на API по подписке.
- Отдельный `catalog/service/normalizer.py` уже складывает `ё` в `е` (`normalize`, строки 152–165), считает стемы и имеет `latin_key`/`token_variants` для нескольких написаний (`latin_key`, `token_variants`, строки 184–204). Эти функции используются извлечением/матчингом каталога, но не SQL-предикатом поиска.
- Поисковые данные не хранятся в едином нормализованном виде: парсер сохраняет `StoreOffer.normalized_title` через `parser/service/utils.normalize_name`, который приводит к lower-case и пунктуации, но не складывает `ё` (`parser_service.py:138–140`, `parser/service/utils.py:15–20`). Каноническое имя товара ищется отдельно.
- Общий предикат используется поиском офферов, каталогом, facets, подсказками товаров и подсказками устройств. `/products/catalog/suggestions` вызывается из поля с задержкой; само поле не должно подменять ввод (`ProductSearchField.tsx:67–85`, `SearchInput.tsx:46–54`).
- В поисковой строке токены OR-ятся по вариантам, слова AND-ятся; буквенно-цифровые модели и числа проходят отдельную граничную regex-логику (`search_predicate.py:50–65`). Каталог сохраняет пользовательскую сортировку по минимальной цене (`comparison_service.py:426–432`). Поисковая выдача офферов может использовать `similarity()` для fuzzy, а обычная сортировка задаётся параметром (`product_service.py:78–89`).

## Архитектурное решение, которое нужно принять до патча

Предпочтительный старт — не добавлять универсальный словарь или зависимость. Раскладка — конечная таблица клавиш; `е/ё` — эквивалентность двух букв; русско-латинская запись уже частично покрыта локальным `latin_key` и тестовыми парами. Это разные операции, их нельзя сводить к одному «исправителю». Сначала проверьте, можно ли безопасно переиспользовать и ограничить текущие варианты в общем SQL-предикате.

Рекомендуемый контракт первого изменения:

1. **Раскладка:** поддерживать английскую↔русскую раскладку для одноязычных буквенных токенов для всех планов. Смешанные буквенно-цифровые токены, SKU и модели не переписывать. Это детерминированная эквивалентность, а не fuzzy исправление опечатки.
2. **`е/ё`:** обеспечить эквивалентность в обе стороны на реальных названиях без переписывания title. Предпочесть query regex с классом `[её]` там, где он совместим с безопасным escaping текущей regex-сборки. PostgreSQL `pg_trgm` GIN поддерживает `~`/`~*`, но regex без извлекаемых триграмм может выродиться в полный index scan; поэтому проверить `EXPLAIN` на репрезентативных запросах. Если план плох, измерить bounded query variants; не использовать column-side `replace()` без проверки индекса. [Документация PostgreSQL `pg_trgm`](https://www.postgresql.org/docs/17/pgtrgm.html).
3. **Транслитерация:** дать детерминированным подтверждённым русско-латинским вариантам доступ для всех планов, оставив fuzzy-опечатки Advanced-only. Проверить `plenka`, `shleyf`, `steklo`, `iphone` и смешанные запросы. Использовать локальную `latin_key`/`token_variants` как поисковые варианты; не менять отображаемые названия и не превращать её неинъективные соответствия в canonical names. Не создавать translit-варианты для произвольных коротких слов или mixed model tokens.
4. **Словарная часть:** сохранить явные продуктовые алиасы/синонимы и их текущие приоритеты. Не заменять словарь деталей общим транслитератором: транслитератор не является словарём синонимов, морфологическим анализатором или исправителем опечаток.

Если внедряемая библиотека всё же рассматривается, сравнить её направление преобразования, варианты обратного преобразования, лицензирование и актуальность именно на русском товарном вводе. Первичные источники на 2026-11-06:

- [CyrTranslit: upstream README](https://github.com/opendatakosovo/cyrillic-transliteration) описывает двусторонний режим и русский язык; [PyPI](https://pypi.org/project/cyrtranslit/) указывает MIT и версию 1.2.0, выпущенную 2025-11-20. Это сильный кандидат для сравнения, но не доказательство совпадения разговорного ввода с вариантами названий магазинов.
- [AnyAscii: upstream README](https://github.com/anyascii/anyascii) и [PyPI](https://pypi.org/project/anyascii/) описывают преобразование Unicode→ASCII посимвенно, без контекста; текущий PyPI релиз 0.3.3, ISC. Сам по себе односторонний выход не закрывает поиск русских названий по латинскому вводу.
- [transliterate PyPI](https://pypi.org/project/transliterate/) поддерживает русский и обратный режим, но указывает последнюю версию 1.10.2 от 2018-09-17 и лицензии GPL 2.0/LGPL 2.1. Не выбирать без отдельной причины и проверки актуальности/лицензионной совместимости.
- [Unidecode upstream README](https://github.com/avian2/unidecode) прямо предупреждает о потере информации и ограничениях посимвольной транслитерации; upstream указывает GPL-2.0-or-later. Не использовать его как готовый поисковый словарь.

**Решение первого PR:** без новой зависимости; использовать локальные функции и явные aliases как источник ограниченных кандидатов. Историческая `docs/technical-specification.md:325–333` помещает транслитерацию в раздел fuzzy; уточнить это требование, чтобы детерминированная эквивалентность скриптов работала на всех планах, а исправление fuzzy-опечаток оставалось Advanced-only. Это вывод из текущей архитектуры и документов upstream, не benchmark производительности.

## Контракт и границы реализации

- Расширения применяются к запросу; пользователю остаётся исходная строка. Не изменять title, `canonical_name`, SKU, URL, результаты парсера или параметры URL.
- Задать конечный бюджет вариантов на токен и запрос, не генерировать декартово произведение произвольной длины; не допускать увеличения числа SQL-клауза без измеримой границы. Сохранять исходную форму как первый/базовый кандидат. Обосновать минимальную длину токена и случаи, когда правило не применяется.
- Сохранить требование AND между словами; OR-варианты должны быть только для того же слова. Не превращать части короткого слова в wildcard. Кандидаты расширения должны только добавлять соответствующие совпадения, а не переписывать существующую выдачу.
- Не менять сортировку карточек, пагинацию и существующий fuzzy-флаг. `min_price_asc`/`min_price_desc` остаются авторитетными; отдельную новую релевантностную сортировку не вводить. Если текущий fuzzy similarity-order требует отдельной обработки expanded query, описать и протестировать точное правило без изменения сортировок каталога.
- Сохранить все существующие фильтры на каждом соответствующем endpoint: устройство, тип детали, качество, магазин, min/max цена, наличие, категория там, где она доступна. Расширенный запрос не должен обходить фильтры facets/suggestions/offers.
- Существующие trigram GIN индексы созданы на `store_offers.normalized_title`, `products.canonical_name`, aliases/synonyms (миграция `backend/alembic/versions/336d8cc4267a_core_offers_canonical_dictionaries_.py:229–248`). Если выбранный `ё`-подход вызывает функции над колонкой или меняет persisted-normalization, проверить query plan/стоимость и обосновать миграцию/backfill; не добавлять миграцию автоматически.
- Существующие UI-компоненты и suggestion debounce менять только если это требуется для контракта; ожидаемая точка реализации — backend query expansion. UI должен продолжать показывать original query, подсказки должны работать тем же способом.

## Acceptance matrix

Terra добавляет регрессионные проверки по матрице ниже и сообщает отдельно unit/API результаты. Данные подбирать так, чтобы каждый положительный контроль имел конкурирующий отрицательный товар.

| Группа | Запрос | Ожидаемое поведение | Отрицательный контроль / инвариант |
|---|---|---|---|
| Раскладка, кириллица | `ddjlt yf lheujv zpsrt` | Находит совпадение для `вводе на другом языке` при точном/частичном поиске согласно принятому тарифному решению | Не срабатывает через один случайный общий символ; токены остаются AND |
| Раскладка, модель | русская раскладка для обычного слова + `iPhone 15 Pro` | Деталь находится; бренд, модель, `15` и `Pro` не становятся ложными вариантами | `iPhone 15` не возвращает `iPhone 14`, `SE` не приравнивается к `XR`, `GT`/`SM-A525`/SKU не совпадают частично |
| `е/ё` | `съемный` ↔ `съёмный`; `емкость` ↔ `ёмкость` | Оба направления находят одинаково нормализованную сущность/оффер в тех же пользовательских фильтрах | Нет false match из-за неограниченного wildcard; mixed query с цифрами сохраняет границы модели |
| Транслит | `plenka`, `shleyf`, `steklo` | Находит русские `пленка/плёнка`, `шлейф`, `стекло`; обратное русское написание находит латинскую запись, если она присутствует в title | Не смешивать `galaxy`/`poco`, `copy`/`original`, `iPhone`/`iPad`; короткие токены и латинские части SKU остаются точными |
| Смешанный ввод | `plenka iPhone 15 Pro`, `плёнка iphone 15` | Каждый токен находит свой кандидат; выдача не требует все слова в одном исходном алфавите | Не допускать OR по всем токенам; чужой бренд/модель отфильтровывается |
| Поведение выдачи | запрос с расширениями плюс `store`, `min_price`, `max_price`, `in_stock`, device/part/quality | Catalog, offers, facets и подсказки сохраняют текущие параметры и возвращают совместимые результаты | Существующая сортировка цены и пагинация не меняются; пустой результат остаётся пустым штатным состоянием |

Позитив/негатив для модели должны включать `iPhone 15 Pro`, `iPhone SE`, `iPhone XR`, `Samsung Galaxy A52 / SM-A525` и разные SKU с общей цифровой частью. Сравнить false positives на базовом наборе и расширенном запросе; не принимать эвристику по одному удачному примеру.

## Сложность и вопросы, которые нельзя замолчать

Оценка: **средняя**, вероятно один backend coder на 0.5–1.5 дня плюс Terra на тесты и reviewer; это оценка, а не committed schedule. Простая часть — reuse/ограничение уже существующих функций. Рискованная часть — двусторонняя `е/ё` совместимость с историческими строками и уникальный SKU/model boundary при OR-расширении. Ввод может смешивать scripts по словам и внутри модели. Пользователь может писать разные версии русской романизации (`ш/щ`, `ж`, `х`, `й/и`), поэтому нельзя обещать универсальное совпадение translit без подтверждённой матрицы.

До production-патча coder/Luna должны подтвердить:

1. `EXPLAIN` для `е/ё` на существующем индексе и пригодность query plan; если он деградирует — выбрать bounded fallback без backfill по умолчанию.
2. порядок исходных/расширенных вариантов внутри текущего fuzzy similarity-order, не меняя сортировку цены и pagination.
3. конечный бюджет candidate terms и порог длины; позитив/негатив матрица должна показать, что budget достаточен и расширения не создали ложных результатов.

Отложить/сузить транслит лучше, чем выдавать результативность за полный словарь: в первом PR можно явно покрыть подтверждённые common spellings, зафиксировать новые aliases в проверяемой таблице и оставить непротестированные варианты как follow-up.
